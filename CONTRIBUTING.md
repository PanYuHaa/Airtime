# Contributing to Airtime

We welcome contributions that improve reconstruction quality, reliability, engineering hygiene, and documentation. This repository follows **Google Engineering Practices** for code review, Python style, testing, and documentation.

---

## 1. Engineering Principles

1. **Zero Hardcoded Paths**: All directory and weight paths must resolve through `airtime.cfg` and environment variables (`AIRTIME_MODELS`, `AIRTIME_CONFIGS`, `AIRTIME_DATA`, `AIRTIME_OUTPUT`, `AIRTIME_GEMX`, `AIRTIME_GEMX_PYTHON`, `AIRTIME_SAM2_PYTHON`).
2. **Declarative Configuration**: Algorithm thresholds and parameters belong in `configs/pipeline.json` (or `configs/style.json`), never scattered as magic numbers in code.
3. **General Rules Only**: Never add video-ID-specific branches or dataset hacks. All heuristics must be general and verifiable across unseen videos.
4. **Determinism First**: Repeated runs on identical input must remain bit-identical. Any change to ONNX/PyTorch execution must preserve deterministic inference (see [ADR-002](docs/adr/002-deterministic-onnxruntime.md)).
5. **Clean Repository Boundaries**: Never commit model checkpoints, raw videos, run outputs, secrets, tokens, or internal-only notes.

---

## 2. Development Setup

```bash
git clone https://github.com/PanYuHaa/Airtime.git
cd Airtime

python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

Run the local verification suite before opening a PR:

```bash
make check
```

---

## 3. Coding Style

We follow the [Google Python Style Guide](https://google.github.io/styleguide/pyguide.html) enforced via `ruff` (`pyproject.toml`):

- **Line length**: 100 characters max.
- **Imports**: Standard library → Third-party → Local package (`airtime`), sorted alphabetically.
- **Type annotations**: Required on new public functions and data contract helpers.
- **Docstrings**: Google-style docstrings explaining contract, arguments, return values, and edge cases.
- **File encoding**: UTF-8, LF line endings (see `.editorconfig`).

---

## 4. Branching & Commit Conventions

- Branch from `main` using descriptive names: `feat/<topic>`, `fix/<topic>`, `docs/<topic>`, `refactor/<topic>`, `test/<topic>`.
- Use [Conventional Commits](https://www.conventionalcommits.org/):
  - `feat:` New feature or pipeline capability
  - `fix:` Bug fix
  - `docs:` Documentation and ADR updates
  - `test:` Unit or regression tests
  - `refactor:` Code restructuring without behavioral change
  - `chore:` Build, CI, tooling, or dependency maintenance

---

## 5. Pull Request Expectations

- Keep PRs small, focused, and reviewable.
- Include unit tests under `tests/` for new logic or bug fixes.
- For changes affecting tracking, pose estimation, or 2D/3D fusion, include a before/after comparison generated by:

```bash
python -m airtime.eval --before runs/baseline --after runs/experiment
```

- Significant architectural changes should include a short ADR under `docs/adr/`.
